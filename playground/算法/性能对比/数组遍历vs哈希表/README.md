# 数组顺序遍历 vs 哈希表索引性能对比

## 问题描述

对于1000个元素的数组，每个元素100字节大小，**元素的key为离散的随机整数**（非连续索引），进行随机读取操作时：
- **方案1**：使用数组顺序遍历查找
- **方案2**：使用哈希表存储元素主键，值为元素在数组中的索引

## 理论分析

### 方案1：数组顺序遍历
- **时间复杂度**：O(n) 平均情况，O(n) 最坏情况
- **空间复杂度**：O(1) 额外空间
- **平均比较次数**：n/2 = 500次
- **特点**：
  - 需要遍历数组直到找到目标元素
  - 每次比较需要访问100字节的元素
  - 对于随机读取，平均需要检查一半的元素
  - **key为离散值，无法利用索引优化，必须完整遍历**

### 方案2：哈希表索引
- **时间复杂度**：O(1) 平均情况，O(n) 最坏情况（哈希冲突时）
- **空间复杂度**：O(n) 额外空间（存储哈希表）
- **平均操作次数**：1次哈希计算 + 1次数组索引访问
- **特点**：
  - 通过哈希表直接定位到数组索引
  - 无需比较元素内容
  - 直接通过索引访问，时间复杂度为O(1)

## 实际测试结果

**哈希表方案明显更快**，实际测试显示：
- **速度提升**：约 **46倍**
- **时间节省**：约 **97.84%**

原因分析：
1. **时间复杂度优势**：O(1) vs O(n)
2. **减少内存访问**：不需要遍历和比较元素内容
3. **离散key场景**：对于离散的随机key，哈希表的优势更加明显，因为数组遍历无法利用任何优化

对于1000个元素的离散key随机读取，哈希表方案显著优于数组遍历。

- 数组大小：1000个元素
- 元素大小：100字节
- 元素key类型：**离散随机整数**（范围：**1 到 10000000**）

## Key=8 字节、Value=8 字节的检索临界点分析

### 场景约定

- **数组方案**：每个元素为 Key(8B) + Value(8B) = **16 字节**，按 Key 顺序遍历查找对应 Value。
- **klib 哈希表方案**：使用 **klib 的 khash.h**（`KHASH_MAP_INIT_INT64`），哈希表 key 8 字节、value 8 字节，单次查找 O(1) 期望。

### 理论分析

| 项目 | 数组 (16B/元素) | klib 哈希表 |
|------|-----------------|-------------|
| 单次查找复杂度 | O(n)，平均比较 n/2 次 | O(1) 期望，1 次 hash + 约 1~2 次探测 |
| 每次比较/访问 | 读 8 字节 key、一次比较；64B cache 行可放 4 个元素，cache 友好 | 哈希计算 + 访问 flags/keys/vals 数组，有固定开销 |
| 临界点形式 | 成本 ∝ α·(n/2) | 成本 ≈ β（常数） |

**临界数量 n\***：当 **α·(n/2) ≈ β** 时，即 **n ≈ 2β/α**。

- **α**：数组方案「一次比较」的开销（含一次 8B 读与分支），在 cache 命中时约 1~3 周期量级。
- **β**：哈希表一次查找的开销（64 位 hash + 1~2 次桶访问 + 可能冲突），约 20~50 周期量级。
- 故 **β/α** 约在 **10~30** 之间，**n\* 约在 20~60** 量级。  
  即：**数据对数量超过约 20~60 时**，按 Key 查 Value 更适合用 klib 哈希表；具体与 CPU、cache、负载因子有关。

### 实测临界点（pair_8_8_bench，使用 klib khash.h）

哈希表方案使用 **klib 的 khash.h**（`KHASH_MAP_INIT_INT64`，8 字节 key、8 字节 value）。`khash.h` 已放在同目录下，无需额外安装。

运行（同目录下需有 `khash.h`）：

```bash
gcc -O2 -o pair_8_8_bench pair_8_8_bench.c -I. && ./pair_8_8_bench
```

典型结果：使用 klib khash 时，**临界点约 N ≈ 4~16**（即数据对数量超过约 4~16 时哈希表即可优于数组）；不同 CPU/cache 下可能略有差异。N 超过该值后，检索按 Key 找 Value 更适合采用 klib 哈希表方案。
