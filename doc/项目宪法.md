# 项目宪法

本文件规定引擎及项目自有模块必须遵守的核心约束。

## 一、生命周期设计原则

### 1.1 生命周期

引擎对外生命周期仅允许以下流程，销毁后可在同一进程重新初始化：

```text
Init → Start → Stop → Destroy
Init → Stop → Destroy
```

- 每轮引擎对外生命周期由同一客户端线程串行控制，不与其他外部引擎操作并发；非法顺序、重复调用或错误线程均致命退出。
- 模块按职责提供 Init／Start／Stop／Destroy，无线程模块只需 Init／Destroy。
- **初始化与启动：** Init 准备固定资源并加载世界，不创建线程，业务时钟保持冻结；Start 使用已备资源，完成启动后才恢复时钟和业务执行。启动完成不等于业务完成。
- **冻结与解冻：** 仅允许客户端线程在运行中调用，不改变生命周期。冻结暂停业务时间，不保证世界停止写入，不能代替 Stop 或作为直接保存、销毁的依据。重复冻结保持原时刻，解冻要求已冻结。
- **停止：** 冻结时钟，退出并回收业务线程，统一结算，最后排空并停止日志。未启动实例不推进时间、不额外结算，仍须停止日志。返回时本轮全部线程已回收，但不保证排队业务全部执行。
- **销毁：** 只处理已停止的引擎实例，不隐式停止。按依赖顺序保存世界、释放资源并复位实例；保存所需数据必须保留到保存完成，存档累计时间不得因实例重建而丢失。

### 1.2 资源与校验

- 资源按所有权释放，实例状态在销毁时立即复位，不留给下一次初始化覆盖；具有独立语义的进程级状态不随实例清空。
- 首次实例必须具备有效空状态，初始化不重复清空已复位状态；业务数据按实际需要分配。
- 公共入口保留独立的访问、参数和状态校验；内部复用已建立且仍有效的前置条件，不重复检查或维护冗余状态。引擎统一管理其所编排模块的生命周期与停止状态。
- 业务约束、必要同步状态及真实资源失败检查必须保留；锁释放后可能变化的条件须重新持锁校验。第三方代码保持原样。

### 1.3 错误与日志

- 可恢复结果与致命错误明确区分，负返回码或错误日志等级不自动意味着退出。实际分配失败、分配大小溢出及必须成功的资源操作失败均须致命退出；断言不能代替公共输入校验或运行期必要检查。
- 致命错误统一直接输出 stderr 并退出，不经日志队列、不等待线程回收，不建立失败回滚、重试或跨线程错误传播链，也不保证保存和清理。
- 生命周期与冻结／解冻操作的非致命诊断直接输出 stdout；业务日志按配置输出，由掌握业务语义的边界记录一次，不逐层重复打印。
- 业务线程退出并完成结算后才停止日志；保存和销毁不再调用日志记录接口。

实现、接口注释与[开发约束](../AGENTS.md)须保持一致。引擎生命周期变更须验证两条合法流程、销毁后重建、非法调用拒绝，以及线程回收、状态复位和日志排空。

## 二、定时器设计原则

### 2.1 职责与时间语义

- **只负责到期通知：** timer 到期后把一次性通知放入业务队列，由业务自行取出并处理，实现异步通知；timer 不执行业务，也不保存业务对象或回调上下文。不提供周期任务、原地改期、存档或离线补算；改期须取消旧请求后重新登记，加载存档后的恢复登记也由业务负责。
- **只累计未冻结的现实时间：** 业务计时使用 32 位毫秒，只有经过校验的业务时刻达到截止点，才算到期；线程被唤醒只是重新检查的机会，不代表已经到期，也不保证恰好在截止点投递。
- **代码独立：** 通用 timer 可以借鉴引擎 timer 的设计，但两者必须保持独立的代码实现。因为让通用timer支持和扩展引擎timer的特有暂停和以及兼容不同队列类型，代码阅读起来会很难受

### 2.2 请求与处理顺序

- **统一排队计时：** 全引擎共用一个计时线程和一个全局最小堆，堆顶保存最早到期的请求。请求依次经过“命令队列 → 全局堆 → 业务事件队列”；目标队列由业务方拥有，并直接随请求传入。
- **记录按值传递：** 命令、堆项和到期消息中的计时记录都直接复制，不保存引用，无需为每条记录单独分配或释放载荷。每次登记使用非零 64 位 `timer_id`，在本次 Init 生命周期内唯一。
- **每批限制处理数量：** 先处理堆项，再把命令队列中的请求移入堆；

### 2.3 同步与取消

- **迁移期间不能漏查取消：** 全局堆的访问、请求迁移和取消共用同一把请求锁。从命令出队到入堆、从堆项移除到业务事件入队，全程持锁，避免取消操作恰好在请求不属于任何容器时查找，误以为请求不存在。
- **进入等待时不能漏掉通知：** 计时线程从确认命令队列为空开始，持续持有请求锁，复查退出、冻结和堆顶后再决定是否等待。条件等待把“释放锁并进入等待”作为一个原子操作，返回前重新取得该锁；发送唤醒通知也必须持有同一把锁，防止通知落在检查结束与开始等待之间。
- **取消只作标记：** 按 `timer_id` 依次查找命令队列、全局堆和登记时使用的业务队列，找到后标记取消，留给相应处理方清理。不另发取消命令、不维护有效 ID 集合，也不直接删除任意堆节点。

### 2.4 冻结、恢复与退出

- **冻结不等待计时线程停下：** 普通冻结只固定 time 的业务时钟，不通知 timer，也不等待其确认。计时线程在批次边界检查退出和冻结，退出优先；已经开始的批次可以继续处理。冻结期间，以及发布停止状态后尚未结束的业务批次，仍可登记和取消请求。
- **恢复沿用原请求：** 解冻时先恢复 time 的业务时钟，再通知 timer，按原截止点继续处理已有请求。启动也遵循这一顺序，并按 1.1 节要求等全部线程创建完成后再解冻。
- **停止只等待线程结束：** 引擎先发布停止状态，再冻结时钟并通知 timer。调用 timer Stop 前，须结束其他 timer API 调用；目标业务队列必须保持可入队，直到 timer Stop 返回。timer Stop 只执行 join，即等待计时线程结束并回收线程资源。

## 三、线程通信消息队列设计原则

### 3.1 核心概念：线程之间的收件箱

queue 可以理解为线程之间共用的“收件箱”：发送者是生产者，调用 `Produce` 投递消息；接收者是消费者，调用 `Consume` 取出消息，再由自己的业务代码处理。发送和处理可以发生在不同时间，入队成功只表示消息已收下，不表示业务已经完成。

- **先入先出：** 支持多个生产者和多个消费者，同一队列按成功入队的先后顺序取出消息（FIFO）。一条消息只被取出一次，多消费者各取各的消息；不保证它们完成业务处理的顺序。
- **通用机制与业务分开：** shared queue 负责存放、取出、等待和通知，不创建线程、不执行业务、不解释冻结或退出状态。引擎收件队列中的 `type` 标明消息种类，`payload` 保存对应内容，由接收模块分派；同一收件箱可以接收 AI、timer 和命令等消息。

### 3.2 存储、容量与并发

- **循环利用槽位：** 消息保存在环形数组中，取走的槽位可继续装新消息，无需每次出队都搬动其余元素。每个队列的元素大小固定，满时按需扩容到配置的上限，并保持 FIFO 顺序。
- **满了或空了怎么办：** 达到容量上限且满载时，`Produce(..., false)` 返回队列满，`Produce(..., true)` 等待空位；正常状态下队列为空时，消费接口同样可选择立即返回或等待消息。所属模块必须处理这些结果。这里的“非阻塞”只表示不等空位或消息，操作仍需取得互斥锁。
- **锁保护队列，出队后的业务在锁外执行：** 入队、出队及队列控制状态由同一把互斥锁保护。条件等待会原子地释放锁并进入等待，返回前重新取得锁；醒来后必须重新检查条件，其他线程可能已抢先取走消息或占用空位。不得持有消费者或通知方需要的业务锁进行阻塞等待。出队后的业务处理在队列锁外执行；队列内消息的取消标记按 2.3 节同步协议处理。
- **按有限批次处理：** 批量出队一次持锁取出当前可用的一批消息，不等待凑满指定数量。业务循环每批限制工作量，在批次边界检查退出和冻结，避免消息持续到来时迟迟无法响应控制状态。

### 3.3 消息复制与资源归属

- **复制消息本身：** 队列按固定字节数复制整条消息，内嵌的值随消息一起复制；指针只复制地址，不会复制它指向的对象。不得向异步消费者传递发送者栈上的地址或可能因容器扩容而失效的地址。
- **资源归属由业务约定：** 例如 AI 行为块在入队成功后才移交所有权，发送者不再访问或释放；入队失败仍归发送者。接收者处理、转交或丢弃消息时负责相应资源。借用的对象（如 timer 的目标队列）则必须由其拥有者保证有效期；队列不会自动释放消息指向的资源。
- **队列 ID 只标识这次投递：** 消息首字段固定为 64 位队列 ID，由队列在成功入队时回写，从 1 开始递增，仅在本队列的一次 Init 生命周期内唯一。它与 timer ID、业务请求 ID 分开；失败不修改消息、不消耗 ID。

### 3.4 等待与唤醒：先记版本，再检查，最后休眠

只需等消息的线程可以使用阻塞消费；还要响应解冻、退出等控制变化的线程，使用 `Snapshot → 检查状态和工作 → Wait`。`Snapshot` 取得 `wake_epoch`，它可以理解为“通知版本”：成功入队、`WakeAll`、`BeginFlush` 都推进版本，出队不推进；它不是消息数量、消息 ID 或业务时间。

1. **先记版本：** 每轮开始先调用 `Snapshot`，记录本轮检查前的通知版本。
2. **再检查和处理：** 先检查退出，再检查冻结；允许运行时处理有限批次的消息和本地工作。还有立即可做的工作就进入下一轮，冻结时则保留消息并准备等待。
3. **最后决定是否休眠：** 调用 `Wait` 并传入先前版本；它在队列锁内比较版本，版本已变就立即返回，否则进入条件等待。返回后重新检查状态和工作；若返回排空状态，则按模块协议退出或清理。

例如，线程刚判断“没有工作”，另一线程就发布退出状态并通知，随后前者才准备睡眠。只检查退出标志会漏掉这次通知；提前记下的版本能让 `Wait` 发现变化，避免睡下后无人再唤醒。因此不能在检查完成后才采样版本，也不能用批次间读取退出／冻结标志代替这套等待协议。

- **唤醒只要求重新检查：** `WakeAll` 不产生消息、不占容量，也不改变队列是否允许入队。通知可以合并，消息也可能已被其他消费者取走，所以醒来不保证有消息。`Wait` 等待版本变化，不以队列非空为条件，冻结时即使箱内留有消息也能休眠；运行时必须先检查工作再等待。
- **先发布状态，再通知：** 模块使用原子操作或自己的锁同步控制状态，再调用 `WakeAll`。引擎解冻和退出须通知相应等待线程；普通冻结不要求立即唤醒或等待线程确认。timer 自身的计时等待仍遵循 2.3 节的请求锁协议。

### 3.5 排空、线程退出与销毁

已初始化队列只有“正常”和“排空”两种运行状态。`BeginFlush` 相当于关闭收件入口：在锁内设置排空状态、推进通知版本并唤醒等待者，已有消息仍可取出。它本身不取消息、不释放载荷，也不等待线程结束；进入后不能恢复生产，只能销毁后重新 Init。

| 操作 | 排空状态下的行为 |
| --- | --- |
| `Produce` | 拒绝新消息；等待空位的生产者醒来后也返回 `ERR_QUEUE_FLUSHING` |
| `Consume`／`ConsumeBatch` | 继续取出已有消息，取空后返回 `ERR_QUEUE_FLUSHING` |
| `Wait` | 立即返回 `ERR_QUEUE_FLUSHING`，不代表消息已经取空 |

- **业务线程退出时可保留收件入口：** 使用版本等待的线程通过“发布退出状态 → `WakeAll` → join”退出。队列保持可投递，让其他线程完成最后一批发送；特别是 timer 的目标队列须遵守 2.4 节。全部相关使用者结束后，再清理残留消息及其资源。引擎 Stop 不保证这些排队业务全部执行。
- **阻塞消费者需要排空协议：** 仅调用 `WakeAll`，空队列上的阻塞消费会检查后继续等待。日志等要求处理完已收消息的模块，须先停止并等待全部生产者，再 `BeginFlush`，由消费者处理剩余消息、收到排空结果后退出，调用方 join。join 表示等待线程结束并回收线程资源。
- **队列为空不等于线程结束：** 消息可能已经取走但仍在处理。销毁前必须确保全部使用者不再访问，完成相关线程的 join，并按业务协议释放残留载荷；等待者计数不能代替这个保证。
- **队列自身只有 Init／Destroy：** 首次对象须为有效零状态，Init／Destroy 期间排除全部并发访问。Destroy 只释放队列存储和同步资源并复位，不隐式排空、唤醒或 join；未启用线程的队列清理载荷后可直接销毁，复位后可再次 Init。

具体参数、返回值和边界契约见 [queue 公共头文件](../shared/include/domino_shared_queue.h)，引擎消息及消费循环示例见 [线程消息说明](../engine/src/queue/README.md)。

## 四、日志模块设计原则

### 4.1 核心概念：多人递交记录，一人负责写出

logger 可以理解为一个有待办箱的记录员：多个业务线程把日志整理好放进队列，每个已启动的日志实例有一个专门的写线程（writer），按入队顺序批量取出并写到文件或控制台。

- **调用方先整理，写线程后输出：** 日志调用先检查模块和等级，再格式化正文、复制来源位置并入队；writer 负责生成输出前缀和写出。需要记录的非空日志正常返回时，表示已经入队，不保证 writer 已经写出或输出流已经刷新。
- **记录按值保存：** 正文、文件名和函数名在调用返回前复制到队列元素中，writer 不借用调用方字符串，也不保存稍后执行的格式化参数。每条记录使用固定大小存储，无需单独分配正文内存。
- **通用服务与引擎接入分开：** shared logger 管理日志队列、模块配置、写线程和文件；engine 只持有自己的实例，提供模块名称、日志宏和生命周期入口。不同实例各有自己的队列、文件资源和日志序号，可以独立使用和停止。

### 4.2 等级决定记不记，配置决定写到哪里

- **先过滤再整理正文：** 等级按 `TRACE → DEBUG → INFO → WARN → ERROR` 递增，达到所属模块的最小等级才记录。例如最小等级为 INFO 时，TRACE 和 DEBUG 被过滤。模块未指定等级时继承实例默认值，实例也未指定时使用 INFO；模块显式指定的等级独立生效，可以比实例默认值更低。
- **一条日志只写一个目标：** 优先使用模块文件，其次实例默认文件，两者都未配置时使用 stdout。所有等级都遵循这一顺序，ERROR 也不会自动改写 stderr 或同时复制到控制台。文件以追加模式打开；明确配置的文件打开失败属于致命错误，不改用其他目标。
- **配置在初始化时确定：** 模块 ID 和名称在同一实例内唯一，Init 解析好每个模块的等级与输出流，之后模块表保持只读。未注册模块、被等级过滤的记录以及公共接口约定的无效输入直接忽略，不占用队列；格式化后为空的正文也不入队。
- **共享输出不保证跨实例顺序：** stdout 由进程共享，不同日志实例之间没有统一的输出顺序。需要分别查看时，为实例或模块配置不同文件。

### 4.3 固定容量，满了就等待空位

日志队列像一个大小固定的待办箱，`buffer_size` 表示可容纳的日志条数。日志使用 queue 时把初始容量和最大容量设为相同值，运行中不扩容；这样日志积压不会持续增加队列内存。

- **不因满载丢弃记录：** 队列满时，当前日志调用先向所属模块的同一输出流同步提示一次并刷新，再通过队列条件变量等待空位，直到本条日志入队。writer 取走记录后唤醒等待者，不用定时轮询，也不覆盖旧记录。
- **满载提示直接写出：** 提示由生产者同步输出，不再进入已经满载的日志队列。因此正常记录交给 writer，但并非所有输出都只发生在 writer 中。
- **异步仍可能让业务等待：** 写出速度跟不上时，生产者会被阻塞，这是保留日志和限制内存占用的明确取舍。调用方须遵守 3.2 节的等待约束，不能持有 writer 继续工作所需的锁。

### 4.4 日志内容与顺序的含义

- **前缀帮助定位：** 输出包含 UTC 时间、线程编号 `tid`、实例日志序号 `seq`、等级、模块及文件／行号／函数位置，再接正文。`tid` 是进程内分配并由线程缓存的数字编号，同一线程写不同实例时保持一致，不是操作系统线程 ID。
- **时间戳是写出时采样的时间：** writer 每批出队后采样一次 UTC 时间，同一批记录共用该时间戳。它不是业务线程调用日志的精确时刻，也不是游戏累计未冻结时间，不能据此计算业务时长。
- **序号不决定输出顺序：** `seq` 在生产线程入队前分配，多线程并发时，先取到序号的线程可能后入队，所以输出序号不保证递增。它与 queue 的消息 ID 分开，也不能当作跨实例的统一业务顺序。
- **长度有限且明确标记截断：** 正文、来源位置和最终输出行都有固定长度限制，超长时截断并带上 `...(TRUNCATED)` 标记。前缀也占用最终行的空间，不能把正文缓冲大小当作一定能完整输出的正文长度。

### 4.5 先准备、再启动，先排空、再释放

日志实例遵循 `Init → Start → Stop → Destroy`，也支持 `Init → Stop → Destroy`。生命周期由调用方串行管理，正常记录日志只允许在 Start 成功后、Stop 前进行。

| 阶段 | 职责 |
| --- | --- |
| `Init` | 校验配置，准备固定队列、模块表和文件，不创建写线程 |
| `Start` | 创建写线程，此后允许多个生产者并发记录日志 |
| `Stop` | 关闭入队，让 writer 写完已收日志并 join，再刷新输出流；保留队列和文件 |
| `Destroy` | 关闭文件、释放队列并复位实例，不隐式 Stop 或 join |

- **先结束生产者，再停止 logger：** Stop 前必须确保本实例的全部日志调用已结束，且不再有新调用。引擎先启动 logger，再启动业务线程；停止时先结束业务线程、完成结算，最后停止 logger。游戏冻结不停止 writer，冻结期间仍可输出日志；保存和销毁期间遵循 1.3 节，不再进入日志队列。
- **排空有明确终点：** Stop 用 `BeginFlush` 拒绝新消息，writer 继续消费剩余记录，队列取空后退出，再由调用方 join。仅 Init、未 Start 时不需要 join，但仍关闭入队并刷新输出。每轮至多 Start 一次，并须 Stop 一次；Stop 后须 Destroy，不能直接重启。
- **刷新与释放分开：** Stop 用 `fflush` 将日志从标准 I/O 缓冲写出，不承诺通过 `fsync` 完成磁盘持久化。Destroy 才关闭文件；多个模块继承的实例默认文件只关闭一次，stdout 只刷新、不关闭。
- **实例存储由调用方负责：** 首次对象须零初始化，Init 后不得复制、移动或直接修改内部成员，地址与存储须保持有效直到 Destroy 返回。Destroy 释放内部资源并清空对象，不释放调用方提供的对象存储，之后可再次 Init。

### 4.6 业务日志、控制诊断与致命错误

输出通道由掌握操作语义的调用点选择，logger 不维护额外阶段标志来切换通道。同一个可恢复结果由业务边界记录一次，不沿调用链重复打印。

| 情况 | 使用方式与效果 |
| --- | --- |
| 运行中的业务记录，包括可恢复的 ERROR | 使用实例日志接口；engine 使用 `DOMINO_ENGINE_LOG`，按模块配置异步输出 |
| 生命周期及冻结／解冻操作的非致命诊断 | 使用 `DOMINO_PRINT_MESSAGE` 直接输出 stdout，不进入日志队列 |
| 致命错误 | 使用 `DOMINO_EXIT_WITH_ERROR` 直接输出 stderr 并退出，不依赖日志线程或排空 |

ERROR 只表示日志等级，不自动终止进程。logger 自身的分配、同步、格式化、文件操作等必要步骤失败时，同样直接走致命退出通道，不能再调用 logger 报告自己的失败。通过过滤的日志若在未 Start 或 Stop 后写入，也属于致命调用错误；致命退出不保证队列中剩余日志全部写出。

具体配置和接口契约见 [logger 公共头文件](../shared/include/domino_shared_logger.h)，引擎调用约定见 [日志接入说明](../engine/src/logger/README.md)。
