# 项目宪法

本文件规定引擎及项目自有模块必须遵守的核心约束。

## 一、生命周期设计原则

### 1.1 生命周期

引擎对外生命周期仅允许以下流程，销毁后可在同一进程重新初始化：

```text
Init → Start → Stop → Destroy
Init → Stop → Destroy
```

- 每轮引擎对外生命周期由同一客户端线程串行控制，不与其他外部引擎操作并发；非法顺序、重复调用或错误线程均致命退出。
- 模块按职责提供 Init／Start／Stop／Destroy，无线程模块只需 Init／Destroy。
- **初始化与启动：** Init 准备固定资源并加载世界，不创建线程，业务时钟保持冻结；Start 使用已备资源，完成启动后才恢复时钟和业务执行。启动完成不等于业务完成。
- **冻结与解冻：** 仅允许客户端线程在运行中调用，不改变生命周期。冻结暂停业务时间，不保证世界停止写入，不能代替 Stop 或作为直接保存、销毁的依据。重复冻结保持原时刻，解冻要求已冻结。
- **停止：** 冻结时钟，退出并回收业务线程，统一结算，最后排空并停止日志。未启动实例不推进时间、不额外结算，仍须停止日志。返回时本轮全部线程已回收，但不保证排队业务全部执行。
- **销毁：** 只处理已停止的引擎实例，不隐式停止。按依赖顺序保存世界、释放资源并复位实例；保存所需数据必须保留到保存完成，存档累计时间不得因实例重建而丢失。

### 1.2 资源与校验

- 资源按所有权释放，实例状态在销毁时立即复位，不留给下一次初始化覆盖；具有独立语义的进程级状态不随实例清空。
- 首次实例必须具备有效空状态，初始化不重复清空已复位状态；业务数据按实际需要分配。
- 公共入口保留独立的访问、参数和状态校验；内部复用已建立且仍有效的前置条件，不重复检查或维护冗余状态。引擎统一管理其所编排模块的生命周期与停止状态。
- 业务约束、必要同步状态及真实资源失败检查必须保留；锁释放后可能变化的条件须重新持锁校验。第三方代码保持原样。

### 1.3 错误与日志

- 可恢复结果与致命错误明确区分，负返回码或错误日志等级不自动意味着退出。实际分配失败、分配大小溢出及必须成功的资源操作失败均须致命退出；断言不能代替公共输入校验或运行期必要检查。
- 致命错误统一直接输出 stderr 并退出，不经日志队列、不等待线程回收，不建立失败回滚、重试或跨线程错误传播链，也不保证保存和清理。
- 生命周期与冻结／解冻操作的非致命诊断直接输出 stdout；业务日志按配置输出，由掌握业务语义的边界记录一次，不逐层重复打印。
- 业务线程退出并完成结算后才停止日志；保存和销毁不再调用日志记录接口。

实现、接口注释与[开发约束](../AGENTS.md)须保持一致。引擎生命周期变更须验证两条合法流程、销毁后重建、非法调用拒绝，以及线程回收、状态复位和日志排空。

## 二、定时器设计原则

### 2.1 职责与时间语义

- **只负责到期通知：** timer 到期后把一次性通知放入业务队列，由业务自行取出并处理，实现异步通知；timer 不执行业务，也不保存业务对象或回调上下文。不提供周期任务、原地改期、存档或离线补算；改期须取消旧请求后重新登记，加载存档后的恢复登记也由业务负责。
- **只累计未冻结的现实时间：** 业务计时使用 32 位毫秒，只有经过校验的业务时刻达到截止点，才算到期；线程被唤醒只是重新检查的机会，不代表已经到期，也不保证恰好在截止点投递。
- **代码独立：** 通用 timer 可以借鉴引擎 timer 的设计，但两者必须保持独立的代码实现。因为让通用timer支持和扩展引擎timer的特有暂停和以及兼容不同队列类型，代码阅读起来会很难受

### 2.2 请求与处理顺序

- **统一排队计时：** 全引擎共用一个计时线程和一个全局最小堆，堆顶保存最早到期的请求。请求依次经过“命令队列 → 全局堆 → 业务事件队列”；目标队列由业务方拥有，并直接随请求传入。
- **记录按值传递：** 命令、堆项和到期消息中的计时记录都直接复制，不保存引用，无需为每条记录单独分配或释放载荷。每次登记使用非零 64 位 `timer_id`，在本次 Init 生命周期内唯一。
- **每批限制处理数量：** 先处理堆项，再把命令队列中的请求移入堆；

### 2.3 同步与取消

- **迁移期间不能漏查取消：** 全局堆的访问、请求迁移和取消共用同一把请求锁。从命令出队到入堆、从堆项移除到业务事件入队，全程持锁，避免取消操作恰好在请求不属于任何容器时查找，误以为请求不存在。
- **进入等待时不能漏掉通知：** 计时线程从确认命令队列为空开始，持续持有请求锁，复查退出、冻结和堆顶后再决定是否等待。条件等待把“释放锁并进入等待”作为一个原子操作，返回前重新取得该锁；发送唤醒通知也必须持有同一把锁，防止通知落在检查结束与开始等待之间。
- **取消只作标记：** 按 `timer_id` 依次查找命令队列、全局堆和登记时使用的业务队列，找到后标记取消，留给相应处理方清理。不另发取消命令、不维护有效 ID 集合，也不直接删除任意堆节点。

### 2.4 冻结、恢复与退出

- **冻结不等待计时线程停下：** 普通冻结只固定 time 的业务时钟，不通知 timer，也不等待其确认。计时线程在批次边界检查退出和冻结，退出优先；已经开始的批次可以继续处理。冻结期间，以及发布停止状态后尚未结束的业务批次，仍可登记和取消请求。
- **恢复沿用原请求：** 解冻时先恢复 time 的业务时钟，再通知 timer，按原截止点继续处理已有请求。启动也遵循这一顺序，并按 1.1 节要求等全部线程就绪后再解冻。
- **停止只等待线程结束：** 引擎先发布停止状态，再冻结时钟并通知 timer。调用 timer Stop 前，须结束其他 timer API 调用；目标业务队列必须保持可入队，直到 timer Stop 返回。timer Stop 只执行 join，即等待计时线程结束并回收线程资源。
